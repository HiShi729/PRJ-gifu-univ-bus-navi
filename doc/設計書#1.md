# 岐大バスナビ 設計書 #1

## 1. アプリタイトル

岐大バスナビ

## 2. アプリの目的

本アプリは、岐阜大学から帰宅する学生を対象に、現在地から各バス停までの移動時間と、岐阜駅方面へ向かうバスの停車順を考慮して、最も早く乗車できるバス停と発車時刻を提示するAndroidアプリである。

岐阜大学構内には、帰宅時に利用する主なバス停として「岐阜大学病院」「柳戸橋」「岐阜大学」がある。岐阜駅方面へ向かうバスは、基本的に「岐阜大学病院 → 柳戸橋 → 岐阜大学」の順に停車する。そのため、授業終了後などの混雑時間帯には、終点寄りの「岐阜大学」バス停ではすでに混雑しており、乗車しづらい場合がある。

本アプリでは、現在時刻、現在地から各バス停までの移動時間、バスの発車時刻、バス停の停車順を組み合わせて、利用者が実際に間に合うバス停を推薦する。

## 3. 想定ユーザー

- 岐阜大学から岐阜駅方面へ帰宅する学生
- 授業終了後に、どのバス停へ向かうべきか迷う学生
- 最寄りのバス停ではなく、手前のバス停へ向かった方が早く乗れる場面を判断したい学生
- 自分が普段使う地点や移動経路を考慮して、現実的に間に合うバスを知りたい学生

## 4. 解決したい課題

通常の時刻表アプリでは、現在時刻以降のバス時刻を表示するだけであり、「今いる場所からそのバス停まで移動して本当に間に合うか」までは判断しにくい。

また、岐阜大学から帰宅する場合、バスは「岐阜大学病院 → 柳戸橋 → 岐阜大学」の順に停車するため、現在地によっては最寄りのバス停ではなく、1つ手前のバス停へ向かった方が早く乗車できる場合がある。

本アプリは、バス停までの移動時間とバスの停車順を考慮して、実際に乗車可能な候補を比較し、最も早く乗れるバス停を提示することでこの課題を解決する。

## 5. アプリの概要

本アプリは、岐阜大学から帰宅する学生を対象に、現在地から「岐阜大学病院」「柳戸橋」「岐阜大学」の三つのバス停までの移動時間と、岐阜駅方面へ向かうバスの停車順を考慮して、最も早く乗車できるバス停と発車時刻を提示するAndroidアプリである。大学構内の地点をノード、地点間の移動時間をエッジとする関係グラフで管理し、Dijkstra法により現在地から各バス停までの最短移動時間を算出する。利用者は自分の研究室などの地点や移動時間を追加できるため、実際の移動経路に基づいて乗車可能な便を判断できる。

## 6. アプリの機能・特徴

主な機能は、現在地ノードの選択、地図上のピン選択、各バス停までの最短移動時間の算出、現在時刻と時刻表を用いた乗車可能便の判定、最短で乗れるバス停の推薦である。さらに、利用者が自分の研究室などの独自ノードを追加し、既存ノードとの移動時間を登録できる。標準エッジの移動時間はユーザー固有の値で上書きできるため、実際の通学動線に合わせた推薦が可能である。授業終了後に岐阜大学バス停が混雑しやすい状況を考慮し、手前のバス停への先回りを支援する点が特徴である。

## 7. 基本仕様

- 現在地
  - 最初の画面に地図を表示し、地図上のピンから現在地を選択できるようにする
  - スタート地点として選択可能なノードから選択できるようにする
  - 建物名、建物入口、ユーザー追加地点などを選択対象とする
  - バス停や経路上の中継専用ノードは、必要に応じてスタート地点候補から除外できるようにする
  - バス停ノードは、地図上では現在地として選択できるようにする
  - プルダウンからも現在地を選択できるようにする
  - よく使う出発地点をプルダウンで選択できるようにする
- 現在時刻
  - 端末の時刻を使用
- 余裕時間
  - 急ぐ: 0分
  - 標準: 1分
  - 安全: 3分
- 雨の日モード
  - 最初の画面に雨の日モードのON/OFFを表示する
  - 岐阜大学の座標を基準に天気予報を取得し、雨予報の場合は自動的にONにする
  - 利用者が手動でON/OFFを変更できるようにする
  - 自動判定と手動変更の関係は、手動変更を優先する
  - 天気予報を取得できない場合は、保存済み設定またはOFFを用いる
- 時刻表データ
  - 開発者が作成したKotlinローカルデータをアプリ内に保持して使用
  - 対象停留所と帰宅方面の便のみを登録して推薦に利用
  - 基本ダイヤとして平日ダイヤ、土日祝ダイヤを持ち、その上に学休日運休、学休日運転、特定期間のみ運行などの追加運行条件を持たせる
- 降車バス停
  - 乗車候補である岐阜大学病院、柳戸橋、岐阜大学以外の停留所から選択できるようにする
  - 選択肢は時刻表データに存在する停留所列から生成する
  - 停留所時刻が存在する便だけを候補として扱う
  - 名鉄岐阜駅を選択した場合でも、JR岐阜駅に停車する便は利用可能候補として扱う
  - 空欄または「-」の停留所時刻は停車なしとして扱う
- 地図上の現在地候補
  - 各CampusGraphNodeに緯度・経度を設定する
  - 最初の画面に地図を表示する
  - 地図上にスタート地点として選択可能なノードのピンを表示する
  - 地図上にはバス停ノードも表示する
  - ピンを選択すると、その地点を現在地として即時に検索できるようにする
- ユーザー追加地点の座標
  - ユーザー追加ノードには座標を設定できるようにする
  - 座標設定方法は、現在地GPSから取得、または緯度・経度の手入力とする
  - 座標が設定されたユーザー追加ノードは、地図上にピン表示できるようにする
- 地図背景
  - 地図画面にはオフラインで表示可能な背景画像を使用する
  - 背景画像はキャンパスマップ画像、航空写真風画像、または簡易地図画像とする
  - 外部地図APIへの通信を前提にしない
- 設定項目
  - 余裕時間、ユーザー追加ノード、移動時間編集、移動時間補正設定は設定ページで管理する
  - 降車バス停、雨の日モード、現在地選択、よく使う出発地点選択は最初の画面から操作できるようにする

## 8. バス停の前提

帰宅時に利用する主なバス停は以下の三つとする。

| バス停名     | 備考                                             |
| ------------ | ------------------------------------------------ |
| 岐阜大学病院 | 帰宅方面バスの最初の停車候補                     |
| 柳戸橋       | 岐阜大学病院と岐阜大学の中間にある停車候補       |
| 岐阜大学     | 終点寄りの停車候補。授業終了後は混雑しやすい想定 |

1. 岐阜大学病院
2. 柳戸橋
3. 岐阜大学

## 9. 推薦ロジック

### 9.1 基本式

バス停到着予想時刻は、以下の式で求める。

バス停到着予想時刻 = 現在時刻 + バス停までの移動時間

乗車可能かどうかは、以下の条件で判定する。

バス停到着予想時刻 + 余裕時間 <= バス発車時刻

この条件を満たす場合、そのバス停の該当便に乗車可能とする。

### 9.2 推薦条件

推薦候補は、以下の優先順位で決定する。

1. 現在日付の基本ダイヤ区分と追加運行条件を満たす便だけを候補にする
2. 利用者が設定した降車バス停に停車する便だけを候補にする
3. ただし、降車バス停として名鉄岐阜駅を選択した場合は、JR岐阜駅に停車する便も利用可能候補として扱う
4. 乗車可能な便だけを候補にする
5. 発車時刻までの余裕時間がマイナスになる候補は、候補一覧にも表示しない
6. 発車時刻が最も早い候補を優先する
7. 発車時刻が同じ場合は、移動時間が短い候補を優先する
8. 余裕時間が少ない場合は注意表示を出す
9. 現在時刻以降に乗車可能な候補がない場合は、「現在時刻以降に乗車可能な便がありません」と表示する
10. 候補一覧には、おすすめとして表示した候補と同一の候補を重複表示しない
11. 検索結果一覧には「理由」を表示しない
12. 検索結果一覧には「降車予定バス停」を表示しない。ただし到着予定時刻の計算には内部的に保持する

### 9.3 判定例

条件:

- 現在時刻: 18:00
- 岐阜大学バス停まで: 5分
- 柳戸橋まで: 8分
- 柳戸橋発: 18:08
- 岐阜大学発: 18:10
- 余裕時間: 0分

到着予想:

- 柳戸橋: 18:08
- 岐阜大学: 18:05

判定:

- 柳戸橋 18:08発には間に合う
- 岐阜大学 18:10発にも間に合う

推薦結果:

- 柳戸橋 18:08発を推薦する

### 9.4 便がない場合の表示

現在時刻、各バス停までの移動時間、余裕時間、時刻表データをもとに判定した結果、乗車可能な候補が一つも存在しない場合は、以下のメッセージを表示する。

現在時刻以降に乗車可能な便がありません

この表示により、利用者に対して、現在の条件では推薦できる便が存在しないことを明確に伝える。

### 9.5 降車バス停による候補絞り込み

利用者は、降車バス停として、時刻表データに存在する停留所列から任意の停留所を選択できる。

ただし、乗車候補である以下の三つの構内バス停は、降車バス停候補から除外する。

- 岐阜大学病院
- 柳戸橋
- 岐阜大学

推薦処理では、選択した降車バス停に停車する便だけを候補にする。

CSV上で空欄または「-」になっている停留所時刻は、当該便がその停留所に停車しないことを意味する。そのため、選択された降車バス停の時刻が空欄または「-」の便は候補に含めない。

ただし、JR岐阜駅と名鉄岐阜駅は近接しているため、名鉄岐阜駅を選択した場合でも、JR岐阜駅に停車する便は利用可能候補として扱う。

一方、JR岐阜駅を選択した場合に名鉄岐阜駅のみ停車する便を候補に含めるかどうかは、MVPでは含めないものとする。

### 9.6 降車予定時刻の表示

推薦結果には、乗車するバス停の発車時刻だけでなく、到着予定時刻も表示する。

例:

- 乗車バス停: 柳戸橋
- 発車時刻: 18:08
- 到着予定時刻: 18:35

便によってはJR岐阜駅には停車するが名鉄岐阜駅には停車しない場合がある。そのため、各便の到着予定時刻はnullableな値として扱い、停車しないバス停については到着予定時刻を持たせない。

### 9.7 おすすめ候補と候補一覧の重複除外

推薦結果画面では、おすすめ候補と候補一覧を分けて表示する。

おすすめ候補として表示した便・乗車バス停の組み合わせは、候補一覧には表示しない。

同一候補の判定は、少なくとも以下の組み合わせで行う。

- tripId
- busStopId
- departureTime

これにより、画面上で同じ候補が「おすすめ」と「候補一覧」の両方に重複して表示されることを防ぐ。

### 9.8 マイナス余裕候補の除外

候補一覧には、発車時刻までの余裕時間が0分以上の候補のみを表示する。

発車時刻までの余裕時間は以下で求める。

発車時刻までの余裕時間 = バス発車時刻 - バス停到着予想時刻 - 余裕時間

この値がマイナスになる場合、利用者はその便に間に合わないため、おすすめ候補にも候補一覧にも表示しない。

ただし、余裕時間が0分の場合は、設定上は乗車可能として扱う。

## 10. 関係グラフ・ユーザー固有移動時間機能

### 10.1 関係グラフによる構内移動時間の管理

大学構内の地点をノード、地点間の移動時間をエッジとする関係グラフとして管理する。

ノードの例:

- 工学部棟入口
- 全学共通教育棟
- 図書館
- 大学会館
- 岐阜大学病院
- 柳戸橋
- 岐阜大学
- ユーザーが追加した研究室

エッジの例:

- 工学部棟入口 -- 全学共通教育棟: 4分
- 全学共通教育棟 -- 柳戸橋: 5分

たとえば、工学部棟入口から柳戸橋へ向かう場合、経路上で全学共通教育棟付近を通るとする。この場合、以下のように区間別に移動時間を登録する。

- 工学部棟入口 -- 全学共通教育棟: 4分
- 全学共通教育棟 -- 柳戸橋: 5分

このとき、工学部棟入口から柳戸橋までの移動時間は、4分 + 5分 = 9分として計算する。

MVPでは、大学構内の移動グラフは無向グラフとして扱う。つまり、地点Aから地点Bへの移動時間と、地点Bから地点Aへの移動時間は同じものとして扱う。

この仕組みにより、単に出発地とバス停の組み合わせごとに固定時間を登録するのではなく、構内の移動経路を複数の区間に分解して管理できる。

### 10.2 ユーザー固有の移動時間設定

利用者は、代表的な1区間について実測した移動時間を登録し、全体の移動時間補正係数を設定できるようにする。

すべての区間を個別入力する必要はない。個別上書きがない標準エッジには、標準エッジ時間にユーザー移動時間補正係数を掛けた補正済み移動時間を使用する。

ただし、必要な場合は特定エッジだけ個別上書きできる。個別上書きは補正係数より優先される。

これにより、同じ地点から同じバス停へ向かう場合でも、利用者本人の普段の移動時間に合わせた推薦が可能になる。

### 10.3 ユーザー移動時間補正係数

ユーザーは、すべてのエッジについて個別に移動時間を入力する必要はない。代表的な1区間について、開発者が設定した標準移動時間と、ユーザーが実際に計測した実測移動時間を比較し、ユーザー移動時間補正係数を算出する。

計算式:

ユーザー移動時間補正係数 = 実測移動時間 ÷ 標準移動時間

例:

- 標準移動時間: A → B = 5分
- ユーザー実測: A → B = 3分
- ユーザー移動時間補正係数: 3 ÷ 5 = 0.6

この場合、ユーザーは標準より速く移動できるとみなし、個別上書きがない他の標準エッジにも 0.6 を掛ける。

例:

- 標準: C → D = 10分
- 補正後: 10 × 0.6 = 6分

移動時間は分単位で扱うため、小数が出た場合は安全側に切り上げる。

例:

- 2.4分 → 3分

移動時間の優先順位:

1. 個別エッジのユーザー上書き時間がある場合は、それを最優先する
2. 個別上書きがない場合は、標準エッジ時間 × ユーザー移動時間補正係数を使う
3. 補正係数が未設定の場合は、標準エッジ時間を使う

補正済みエッジ時間:

- 個別上書きがある場合: 個別上書き時間
- 個別上書きがない場合: ceil(標準エッジ時間 × ユーザー移動時間補正係数)
- 補正係数がない場合: 標準エッジ時間

注意:

- 全区間で同じ比率で速いまたは遅いと仮定する簡易補正である
- 屋内、屋外、階段、信号、混雑などによる差は完全には反映しない
- ただし、ユーザー入力を1回で済ませられるため、実用性が高い
- 必要に応じて、個別エッジ上書きにより例外的な区間だけ調整できる

### 10.4 ユーザーによるノード追加

利用者は、開発者が用意した標準ノードに加えて、自分専用の地点をノードとして追加できるようにする。

例:

- 自分の研究室
- よく利用する駐輪場
- サークル棟
- 特定の建物入口

たとえば、利用者が「自分の研究室」をノードとして追加し、「自分の研究室 -- 工学部棟入口」の移動時間を3分として登録する。この場合、アプリは以下のように既存の構内移動グラフへユーザー追加ノードとエッジを接続する。

- 自分の研究室 -- 工学部棟入口: 3分
- 工学部棟入口 -- 全学共通教育棟: 4分
- 全学共通教育棟 -- 柳戸橋: 5分

この場合、自分の研究室から柳戸橋までの移動時間は、3分 + 4分 + 5分 = 12分として計算する。

ユーザーが追加したノードおよびエッジは、開発者が用意した標準グラフに追加する形で扱う。標準エッジと同じ区間に個別上書き時間がある場合は、個別上書き時間を優先する。

### 10.5 経路探索方法

MVPでは、地点間の関係グラフを用いて、出発ノードから各バス停ノードまでの最短移動時間を求める。

経路探索にはDijkstra法を用いる。各エッジの重みは、標準エッジ時間、ユーザー移動時間補正係数、個別エッジ上書き時間から算出した補正済み移動時間の分数とし、出発ノードから目的のバス停ノードまでの合計移動時間が最小となる経路を求める。

探索対象のバス停ノードは以下の三つとする。

- 岐阜大学病院
- 柳戸橋
- 岐阜大学

推薦処理では、まず現在地ノードから三つのバス停ノードまでの最短移動時間を計算し、その後、現在時刻、余裕時間、各バス停の発車時刻を用いて乗車可能判定を行う。

### 10.6 スタート地点として選択可能なノード

構内移動グラフでは、すべてのノードがスタート地点として適切とは限らない。

たとえば、建物入口やユーザーが追加した研究室はスタート地点として選択できる。一方、経路探索のためだけに用意した中継地点は、スタート地点候補として表示しない。

そのため、各CampusGraphNodeには、スタート地点として選択できるかどうかを表す属性を持たせる。

選択可能な例:

- 工学部棟入口
- 全学共通教育棟
- 図書館
- 大学会館
- 自分の研究室
- よく使う駐輪場

選択不可の例:

- 経路探索用の中継ノード
- 通路や交差点など、ユーザーが通常選択しない地点

HomeScreenの現在地選択欄には、スタート地点として選択可能なノードのみを表示する。ただし、地図画面ではバス停ノードも選択可能にする。

### 10.7 地図上での地点選択

各CampusGraphNodeには緯度・経度を設定できるようにする。

地図画面では、スタート地点として選択可能な通常ノード、ユーザー追加ノード、バス停ノードをピンとして表示する。利用者がピンを選択すると、その地点を現在地として即時に検索し、検索結果画面へ遷移する。

MVPでは、外部地図APIやオンライン地図タイルは使用せず、オフラインで表示可能な背景画像またはCanvasによる簡易地図背景を使用する。

### 10.8 オフライン地図背景

地図画面では、ピンだけでなく背景画像を表示する。

背景画像は、アプリ内リソースとして保持し、オフラインで表示できるようにする。外部地図APIやオンライン地図タイルの取得はMVPでは使用しない。

背景画像の候補は以下とする。

- キャンパスマップ画像
- 航空写真風の静的画像
- 開発者が作成した簡易地図画像

20. CampusGraphNodeの緯度・経度をもとに、オフライン地図背景またはCanvas背景上へピンを表示し、ピン選択で現在地として検索できるようにする

### 10.8.1 地図背景の座標境界

地図背景画像にGPS座標を重ねるため、大学敷地を囲む基準座標を以下のように設定する。

| 位置 |      緯度 |       経度 |
| ---- | --------: | ---------: |
| 左上 | 35.469972 | 136.732333 |
| 右下 | 35.459833 | 136.742528 |

元の座標表記:

- 左上: 35°28'11.9"N 136°43'56.4"E
- 右下: 35°27'35.4"N 136°44'33.1"E

アプリ内部では、上記を10進数の緯度・経度として扱う。

### 10.8.2 地図座標から画面座標への変換

地図背景画像の左上を画面座標の原点とし、右下までの範囲に緯度・経度を線形変換してピンを配置する。

変換式は以下とする。

x = (longitude - leftLongitude) / (rightLongitude - leftLongitude) \* mapWidth

y = (topLatitude - latitude) / (topLatitude - bottomLatitude) \* mapHeight

ここで、各値は以下を意味する。

| 変数           | 内容               |
| -------------- | ------------------ |
| latitude       | 対象地点の緯度     |
| longitude      | 対象地点の経度     |
| topLatitude    | 左上座標の緯度     |
| bottomLatitude | 右下座標の緯度     |
| leftLongitude  | 左上座標の経度     |
| rightLongitude | 右下座標の経度     |
| mapWidth       | 地図表示領域の幅   |
| mapHeight      | 地図表示領域の高さ |

緯度は北に行くほど値が大きくなる一方、画面座標のyは下に行くほど大きくなるため、y座標の変換では topLatitude - latitude を用いる。

座標が上記の境界範囲外にある場合は、地図上に表示しない、または地図端に丸めて表示する。MVPでは表示しない方針とする。

### 10.9 地図ピン選択時の即時検索

地図画面で地点ピンを選択した場合、その地点を現在地として設定し、確認ボタンを挟まずに検索結果画面へ遷移する。

処理順序は以下の通りとする。

1. 利用者が地図上のピンをタップする
2. タップされたノードIDを現在地として設定する
3. 現在の設定ページで選択されている降車バス停・余裕時間を利用する
4. 推薦検索を実行する
5. 検索結果画面へ遷移する

### 10.10 バス停ノードの地図表示と選択

地図画面には、スタート地点として選択可能な通常ノードだけでなく、バス停ノードも表示する。

バス停ノードは、通常ノードとは見た目を分けて表示する。

例:

- 通常ノード: 通常ピン
- バス停ノード: バス停用ピン

バス停ノードも、地図上で選択できるようにする。これにより、利用者は「岐阜大学バス停から柳戸橋または岐阜大学病院まで、今から移動して間に合うか」を確認できる。

ただし、HomeScreenの現在地Dropdownにバス停ノードを表示するかどうかは別管理とする。地図画面ではバス停ノードも選択可能にするが、Dropdownでは従来通りisSelectableAsStartがtrueのノードを基本とする。

### 10.11 岐阜大学座標に基づく雨予報判定

雨の日モードは、利用者の手動設定に加えて、岐阜大学の座標に基づく天気予報から自動判定できるようにする。

天気予報取得に使用する基準座標は、岐阜大学バス停の座標を用いる。

| 基準地点       |      緯度 |       経度 |
| -------------- | --------: | ---------: |
| 岐阜大学バス停 | 35.462718 | 136.736083 |

天気予報データで現在時刻付近または直近数時間に雨が予測される場合、雨の日モードを自動的にONにする。

ただし、利用者が手動で雨の日モードを変更した場合は、手動設定を優先する。

天気予報の取得に失敗した場合、アプリはクラッシュせず、保存済みの雨の日モード設定またはOFFを用いる。

天気予報取得にはネットワーク通信を使用するため、AndroidManifestにインターネット権限を追加する。外部APIキーが必要なサービスは避け、APIキー不要で利用できる天気予報APIを優先する。

## 12. データ設計案

### 12.0 ローカル時刻表データ利用方針

時刻表データは、開発者が作成したKotlinローカルデータを利用する。外部データをそのまま読み込むのではなく、本アプリで必要な停留所、便、発車時刻、運行条件のみを事前に整理してアプリ内に保持する。

対象とする停留所は以下の三つとする。

| 停留所       | 扱い                               |
| ------------ | ---------------------------------- |
| 岐阜大学病院 | ローカルデータに発車時刻を登録する |
| 柳戸橋       | ローカルデータに発車時刻を登録する |
| 岐阜大学     | ローカルデータに発車時刻を登録する |

本アプリでは、帰宅方面で利用する三つのバス停を対象とし、停車順が「岐阜大学病院 → 柳戸橋 → 岐阜大学」となる便を推薦対象とする。

ローカル時刻表データは、アプリ内部で扱いやすいBusTrip形式で保持する。

### 12.0.1 運行条件の扱い

時刻表は、まず基本ダイヤとして平日ダイヤ、土日祝ダイヤを持つ。その上で、各便に対して以下のような追加運行条件が存在することを想定する。

| 追加運行条件           | 内容                                                       |
| ---------------------- | ---------------------------------------------------------- |
| 追加条件なし           | 基本ダイヤの曜日区分に従って運行する                       |
| 学休日運休             | 基本ダイヤ上は運行日であっても、学休日には運行しない       |
| 学休日運転             | 基本ダイヤ上の該当日であり、かつ学休日の場合のみ運行する   |
| 期間限定運行           | 毎年4月から8月のみ運行するなど、特定期間だけ運行する       |
| 期間限定かつ学休日運休 | 指定期間内で、学休日以外の日に運行する                     |
| 連接バスの可能性あり   | 該当便が連接バスで運行される可能性があることを示す補助属性 |

そのため、各BusTripには、発車時刻、基本ダイヤ区分、追加運行条件を持たせる。推薦処理では、まず現在日付が平日ダイヤまたは土日祝ダイヤのどちらに該当するかを判定し、その後、学休日運休・学休日運転・期間限定運行などの追加条件を満たす便だけを候補に含める。連接バスの可能性は運行可否の判定条件ではなく、利用者に表示する補助情報として扱う。

### 12.0.2 日付判定に必要な情報

運行条件を判定するため、アプリでは以下の情報を扱う。

| 情報                | 内容                                                                 |
| ------------------- | -------------------------------------------------------------------- |
| baseDayType         | 平日ダイヤ・土日祝ダイヤの分類                                       |
| isSchoolHoliday     | 学休日かどうか                                                       |
| operatingStartMonth | 運行開始月                                                           |
| operatingEndMonth   | 運行終了月                                                           |
| operationRule       | 追加条件なし、学休日運休、学休日運転、期間限定運行などの追加運行条件 |

MVPでは、学休日の日付一覧は開発者がローカルデータとして登録する。祝日判定や大学カレンダーとの自動連携は発展機能とする。

日付判定の順序は以下の通りとする。

1. 現在日付が平日か土日祝かを判定する
2. BusTripの基本ダイヤ区分と一致する便だけを候補にする
3. 現在日付が学休日一覧に含まれるかを判定する
4. 学休日運休、学休日運転などの追加運行条件を判定する
5. 期間限定運行の場合は、現在月が運行開始月から運行終了月の範囲内かを判定する
6. すべての条件を満たす便のみ推薦候補に含める

### 12.3 CampusGraphEdge

地点間の移動時間を表すエッジデータ。

| 項目                    | 内容                                             |
| ----------------------- | ------------------------------------------------ |
| id                      | エッジID                                         |
| fromNodeId              | 始点ノードID                                     |
| toNodeId                | 終点ノードID                                     |
| minutes                 | 開発者が設定した標準移動時間                     |
| isBidirectional         | 双方向移動可能かどうか。MVPではtrueを基本とする  |
| sourceType              | 標準エッジ、ユーザー追加エッジなどの分類         |
| isSelectableForUserEdit | ユーザーが移動時間を編集できるエッジの場合はtrue |

エッジは、スタート地点として選択する対象ではなく、地点間の移動時間を表す接続情報として扱う。

minutesは開発者が設定した標準移動時間を表す。実際にDijkstra法で使う重みは、個別エッジ上書きまたはユーザー移動時間補正係数を反映した補正済み移動時間である。補正済み移動時間は、Dijkstra法に渡す前に計算する。

ただし、ユーザーが移動時間を編集できるエッジと編集できないエッジは分ける。

編集可能な例:

- 工学部棟入口 -- 全学共通教育棟
- 全学共通教育棟 -- 柳戸橋
- 図書館 -- 岐阜大学

編集不可の例:

- システム内部で経路探索用に必要な補助エッジ
- バス停内部処理用の接続エッジ

EditTravelTimeScreenでは、isSelectableForUserEditがtrueのエッジのみを表示する。

| id                     | ユーザー追加ノードID                                   |
| name                   | 利用者が入力した地点名                                 |
| connectedNodeId        | 既存グラフ内で接続する標準ノードID                     |
| minutesToConnectedNode | 接続先ノードまでの移動時間                             |
| isSelectableAsStart    | ユーザー追加ノードを現在地として選択できる場合はtrue   |
| latitude               | ユーザー追加ノードの緯度。未設定の場合は地図ピン非表示 |
| longitude              | ユーザー追加ノードの経度。未設定の場合は地図ピン非表示 |
| coordinateSource       | GPS取得、手入力、未設定などの座標設定方法              |

例:

- name: 自分の研究室
- connectedNodeId: 工学部棟入口
- minutesToConnectedNode: 3

このデータをもとに、「自分の研究室 -- 工学部棟入口」というユーザー追加エッジを構内移動グラフへ追加する。

### 12.4.1 UserNodeCoordinateSource

ユーザー追加ノードの座標設定方法を表すデータ。

| 値     | 内容               |
| ------ | ------------------ |
| NONE   | 座標未設定         |
| GPS    | 現在地GPSから取得  |
| MANUAL | 緯度・経度を手入力 |

MVPでは、GPS取得が実装困難な場合でも、緯度・経度の手入力は実装する。

### 12.5 DestinationBusStop

利用者が選択する降車バス停を表すデータ。

| 値            | 内容       |
| ------------- | ---------- |
| JR_GIFU       | JR岐阜駅   |
| MEITETSU_GIFU | 名鉄岐阜駅 |

降車バス停としてMEITETSU_GIFUが選択された場合でも、JR_GIFUに停車する便は候補として扱う。

### 12.6 BusStopCandidateへの追加項目

推薦候補には、以下の項目を追加する。

| 項目                   | 内容                                   |
| ---------------------- | -------------------------------------- |
| destinationBusStop     | 利用者が設定した降車バス停             |
| actualArrivalBusStop   | 到着予定時刻の基準となる降車バス停     |
| destinationArrivalTime | 到着予定時刻                           |
| mayBeArticulatedBus    | 連接バスとして運行される可能性があるか |

名鉄岐阜駅を選択したが、JR岐阜駅停車便を候補として扱う場合、destinationBusStopはMEITETSU_GIFU、actualArrivalBusStopはJR_GIFUとする。

ただし、ResultScreenの一覧表示では、reasonとdestinationBusStopは表示しない。これらは内部判定やデバッグ用の情報として保持してよい。

### 12.7 UserTravelTimeProfile

ユーザー移動時間補正係数を表すデータ。

| 項目              | 内容                                               |
| ----------------- | -------------------------------------------------- |
| calibrationEdgeId | 補正計算に使った基準エッジID                       |
| standardMinutes   | 基準エッジの標準移動時間                           |
| measuredMinutes   | ユーザーが実測した移動時間                         |
| timeScaleFactor   | measuredMinutes ÷ standardMinutes で求めた補正係数 |

補正係数が未設定の場合は、標準エッジ時間をそのまま使う。

## 13. 最小実装範囲

1. 現在地を建物名から選択する
2. 開発者が作成したKotlinローカル時刻表データを保持する
3. 平日ダイヤ・土日祝ダイヤの基本ダイヤ区分に加えて、学休日運休、学休日運転、期間限定運行などの追加運行条件を判定できる構造を用意する
4. 連接バスの可能性をBusTripの補助属性として保持し、結果表示に反映できるようにする
5. 地点をノード、地点間の移動時間をエッジとする関係グラフを用意する
6. Dijkstra法により、現在地ノードから各バス停ノードまでの最短移動時間を計算する
7. 代表的な1区間の標準移動時間と実測移動時間から、ユーザー移動時間補正係数を算出できるようにする
8. 個別上書きがないエッジには、ユーザー移動時間補正係数を適用する
9. 個別エッジ上書きがある場合は、補正係数より個別上書き値を優先する
10. Dijkstra法には、補正済みエッジ時間を重みとして渡す
11. ユーザーが自分の研究室などの独自ノードを追加し、既存ノードへ接続できるようにする
12. 現在地選択欄には、isSelectableAsStartがtrueのノードのみを表示する
13. 現在時刻から乗車可能な便を判定する
14. 発車時刻までの余裕時間がマイナスになる候補は表示しない
15. 最初の画面に地図を表示し、地図上のピンから現在地を選択できるようにする
16. 最初の画面で雨の日モードをON/OFFできるようにする
17. 岐阜大学の座標に基づく天気予報から雨の日モードを自動ONにできるようにする
18. よく使う出発地点をプルダウンで選択できるようにする
19. 降車バス停は、岐阜大学病院、柳戸橋、岐阜大学以外の時刻表停留所から選択できるようにする
20. 最も早く乗れるバス停と発車時刻を表示する
21. 候補比較を推薦結果画面内に表示する
22. 降車バス停としてJR岐阜駅または名鉄岐阜駅を選択できるようにし、選択した降車バス停に停車する便だけを候補として表示する
23. 推薦結果に到着予定時刻を表示する
24. 降車バス停、余裕時間、ユーザー追加ノード、移動時間編集は設定ページで管理する
25. 設定画面から移動時間補正設定画面へ遷移できるようにする
26. CampusGraphNodeの緯度・経度をもとに地図または擬似地図へピンを表示し、ピン選択で現在地候補を選べるようにする
27. 地図画面にはオフラインで表示可能な背景画像を表示する
28. 地図背景の左上座標と右下座標をもとに、緯度・経度を画面上のx,y座標へ線形変換してピンを配置する
29. 岐阜大学、柳戸橋、岐阜大学病院のバス停ノードには実測座標を設定する
30. 地図上のピンをタップしたら、その地点を現在地として即時に検索し、検索結果画面へ遷移する
31. 地図上にはバス停ノードも表示し、バス停ノードも現在地として選択できるようにする
32. ユーザー追加ノードには、GPS取得または緯度・経度手入力で座標を設定できるようにする
33. 検索結果一覧には理由を表示しない
34. 検索結果一覧には降車予定バス停を表示しない
35. 候補一覧には、おすすめとして表示した候補と同一の候補を表示しない
36. 乗車可能な便がない場合は「現在時刻以降に乗車可能な便がありません」と表示する

## 16.1 Git運用方針

本プロジェクトでは、`main` ブランチを安定版、`develop` ブランチを開発統合用ブランチとして扱う。

機能追加や修正を行う場合は、`develop` から作業用の `feature` ブランチを作成し、そのブランチ上で作業する。

### 16.1.1 基本方針

- `main` ブランチは提出可能な安定版として扱う
- `develop` ブランチは開発中の統合ブランチとして扱う
- 修正作業は `develop` から作成した `feature` ブランチ上で行う
- 修正途中では `develop` にマージしない
- 修正が完全に完了するまでは、同じ `feature` ブランチ上にコミットを積む
- すべての修正が完了し、ビルドとテストが通った段階でのみ `develop` にマージする
- `develop` へのマージは merge commit 方式で行う
- fast-forward merge は使わない
- merge commit には `--no-ff` を使う
- `main` には提出直前までマージしない

### 16.1.2 修正作業時の手順

例として、地図座標修正を行う場合は以下のように進める。

```text
git status
git branch

git checkout develop
git checkout -b feature/fix-map-coordinate-projection
```

作業中は、`feature/fix-map-coordinate-projection` 上で修正を行う。

修正ごとにビルド・テストを確認する。

```text
./gradlew test --no-daemon
./gradlew build --no-daemon
```

JDKの問題が出る場合は、必要に応じて `JAVA_HOME` と `ORG_GRADLE_PROJECT_org_gradle_java_home` を明示する。

ビルドとテストが通る状態で、意味のある単位でコミットする。

```text
git add .
git commit -m "fix: correct campus map coordinate projection"
```

追加修正が残っている場合は、`develop` へマージせず、同じ `feature` ブランチ上で作業を継続する。

### 16.1.3 developへのマージ条件

`feature` ブランチを `develop` にマージするのは、以下の条件をすべて満たした場合のみとする。

- 予定していた修正がすべて完了している
- `./gradlew test --no-daemon` が成功している
- `./gradlew build --no-daemon` が成功している
- 不要なビルド成果物、ローカル環境依存ファイル、IDE固有の不要ファイルがコミット対象に含まれていない
- 既存機能が壊れていないことを手動確認している

条件を満たした後、以下のように `develop` へ merge commit 方式でマージする。

```text
git checkout develop
git merge --no-ff feature/fix-map-coordinate-projection -m "merge: feature/fix-map-coordinate-projection into develop"
```

### 16.1.4 Codexへ修正依頼する際のGit指示

Codexへ修正を依頼する場合は、以下の方針を明記する。

- 作業前に `git status` と `git branch` を確認する
- `develop` ブランチから作業ブランチを作成する
- 実装作業は作業ブランチ上で行う
- 修正途中では `develop` にマージしない
- 修正が完全に終わるまでは、同じ作業ブランチ上でコミットを積む
- ビルドやテストが失敗している状態ではコミットしない
- すべての修正が完了し、ビルドとテストが通った段階でのみ、作業ブランチを `develop` に `--no-ff` でマージする
- `main` にはマージしない
